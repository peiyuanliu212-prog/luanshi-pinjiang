# 《乱世拼将》图鉴人物图性能专项：真懒加载修复设计

- 日期：2026-11-19
- 分析对象：仓库根目录单文件 `index.html`（本次读取为 5,066 行、3,887,340 B）
- 范围：图鉴人物头像的挂图时机、视口观察、两张头像精灵图的分发方式
- 红线：不改玩法、数值、存档结构和既有 `localStorage` key；不改变图鉴以外的图片机制；虎扑单文件分发的可用性优先
- 本轮状态：只完成代码核对、基线测量和设计，未修改 `index.html`

## 1. 结论与建议

三处问题均成立：

1. `.avatar[data-lazy-pos]` 没有覆盖 `background-image`，所以带有懒加载标记的格子在 CSS 层叠后仍引用精灵图。
2. `renderGallery()` 同步挂 24 格，再通过 `requestIdleCallback` 把其余 66 格全部挂完，完全不检查视口；`IntersectionObserver` 因而失去决定挂图时机的作用。
3. 两张 WebP 精灵图以 data URI 内联在两条共享 CSS 规则中，base64 文本合计 **849,072 B（约 829.2 KiB）**，随 HTML 必下，解码调度无法推迟这部分 HTML 下载。

建议分两步走：

- **虎扑单文件版本先落地 D1 + D2，D3 保持内联。** 这一步能真正阻止屏外格子挂图，不改变分发形态，也不影响非图鉴头像的资源路径。
- **外置只在平台能力验证后作为独立分发变体推进。** 若虎扑只接收一个 HTML、没有可靠的静态资源/CDN 能力，外置会直接破坏头像可用性。若为了运行时降级仍把 base64 留在同一个 HTML 中，则又失去减重收益。

本次桌面基线的首开和滚动已经很快，但 90 格被全量挂图是确定事实。高配置桌面无掉帧不能替代虎扑安卓真机结果，也不能证明当前的假懒加载合理。

## 2. 代码核对与实际证据

### 2.1 D1：懒加载格子仍引用精灵图——确认

相关位置：

- [index.html#L214-L217](../index.html#L214-L217)：`.avatar` 定义第一张精灵图，实际 `background-image` 在第 215 行。
- [index.html#L218-L222](../index.html#L218-L222)：`.avatar[data-lazy-pos]` 只重复尺寸、边框、背景色等声明，**没有 `background-image: none`**。
- [index.html#L223](../index.html#L223)：`.avatar.b2` 定义第二张精灵图。
- [index.html#L1563-L1566](../index.html#L1563-L1566)：`avatarLazyHTML()` 只输出 `data-lazy-pos`，没有内联关闭背景图。
- [index.html#L1599-L1600](../index.html#L1599-L1600) 与 [index.html#L4355](../index.html#L4355)：所谓“挂图”只是设置 `background-position` 并移除 `data-lazy-pos`。

简化后的当前 CSS 关系如下，base64 内容省略：

```css
.avatar {
  background-image: url("data:image/webp;base64,...");
}

.avatar[data-lazy-pos] {
  /* 没有 background-image 声明 */
}

.avatar.b2 {
  background-image: url("data:image/webp;base64,...");
}
```

`background-image` 不是从父元素继承，而是同一样式表中多条规则共同层叠：更具体的懒加载规则没有给出新值，因此 `.avatar` 的值仍然生效；第二组头像还命中 `.avatar.b2`。

浏览器 CSSOM 复核结果也一致：

| 选择器 | CSSOM 中自身的 `backgroundImage` |
| --- | --- |
| `.avatar` | `url("data:image/webp;base64,...")` |
| `.avatar[data-lazy-pos]` | 空 |
| `.avatar.b2` | `url("data:image/webp;base64,...")` |

因此，当前 `data-lazy-pos` 并没有达成注释所称“未进视口的格先不引用精灵图”。

另一个实现细节：`.avatar[data-lazy-pos]` 与 `.avatar.b2` 都是两个类/属性级 specificity，且 `.avatar.b2` 位于后方。若只在现有第 219 行规则里简单补 `background-image: none`，第二组头像仍可能被后面的 `.avatar.b2` 覆盖。修法必须处理这个顺序问题，见 4.1。

### 2.2 D2：空闲分片绕过视口，IO 失去作用——确认

相关位置：

- [index.html#L4313](../index.html#L4313)：`__GAL_BATCH = 24`。
- [index.html#L4337-L4348](../index.html#L4337-L4348)：一次生成全部 6 势力、90 个人物格的 HTML。本轮不需要把这一点改成虚拟列表；问题在背景图挂载，不在是否存在 90 个轻量 DOM 格。
- [index.html#L4353-L4356](../index.html#L4353-L4356)：收集全部 90 个懒加载格，立即挂载前 24 格。
- [index.html#L4357-L4365](../index.html#L4357-L4365)：剩余格进入 `requestIdleCallback` 分片；每轮只按“本轮是否少于 8ms”停止，直到 `rest` 为空，没有可见性判断。
- [index.html#L4367](../index.html#L4367)：上述全量任务已经安排后才调用 `__galObserve()`。
- [index.html#L1590-L1605](../index.html#L1590-L1605)：IO 只会处理回调时仍带 `data-lazy-pos` 的元素；空闲分片却独立移除同一属性，完全绕过 IO。
- [index.html#L4386](../index.html#L4386)：`renderGallery()` 在 `showScreen('gallery')` 前执行，因此当前观察器还是在图鉴仍为 `display:none` 时创建的。显示后浏览器通常会重新计算交叉，但把观察放到可见之后更明确、更易验证。
- [index.html#L67-L68](../index.html#L67-L68) 与 [index.html#L198-L199](../index.html#L198-L199)：`content-visibility:auto` 可减少屏外布局/绘制，但不会撤销 CSS 中的图片 URL，也不能代替懒加载。

`window.__galRendered` 在第 4354 行归零，只在第 4355 行的 `mount()` 中递增；IO 分支当前不递增该计数。因此它目前实际表示“首批 + 空闲分片挂载数”，不是完整的“所有方式已挂载数”。修复时应统一语义，见 4.2。

### 2.3 D3：两张精灵图随 HTML 必下——确认

从当前两条 data URI 实际解码得到：

| CSS 行 | 用途 | base64 字符数 | WebP 字节数 | 尺寸 | WebP SHA-256 前缀 |
| --- | --- | ---: | ---: | --- | --- |
| [215](../index.html#L215) | `.avatar`，第一组 21 人 | 307,008 | 230,256 B（约 224.9 KiB） | 1280×731 | `fba3bdfd02d80a7d` |
| [223](../index.html#L223) | `.avatar.b2`，第二组 69 人 | 542,064 | 406,546 B（约 397.0 KiB） | 1200×1421 | `193e037e0ff342c6` |
| 合计 | 两张图 | **849,072 B** | **636,802 B（约 621.9 KiB）** | — | — |

两张图的 base64 文本约占整个 HTML 原始字节的 **21.8%**。base64 相对二进制增加约三分之一文本量；实际线上压缩后的节省需以相同 Content-Encoding 重新测量，不能直接把原始字节差当成线上流量差。

[index.html#L1569-L1587](../index.html#L1569-L1587) 只是从 CSSOM 取 data URI；[index.html#L1601-L1602](../index.html#L1601-L1602) 和 [index.html#L2993-L2997](../index.html#L2993-L2997) 只把解码放进队列。它们既不能从 HTML 中移除 base64，也不能减少 HTML 下载。data URI 也不会表现为独立的普通 HTTP Resource Timing 条目。

还需注意：`avatarHTML()` 及同一对 `.avatar` / `.avatar.b2` 规则也用于图鉴以外，例如 [index.html#L1555-L1560](../index.html#L1555-L1560)、[index.html#L1625](../index.html#L1625)、[index.html#L1647](../index.html#L1647) 和 [index.html#L4379](../index.html#L4379)。这直接决定 D3 的取舍：

> 若只在图鉴作用域改用外链，却为了让非图鉴头像保持原样而继续保留全局两条 base64，HTML 并不会减重，反而可能同时持有外链与 data URI 两份资源。真正减少 HTML 体积，必须替换共享规则的 URL，并回归验证非图鉴头像。

仓库中的 `palace/assets/avatar-sprite-2.webp` 为 1440×1600、422,964 B，哈希也不同，不是当前第二张图，不能直接拿来替换。外置文件应从上述当前 data URI 原样解码生成。

- 测试上下文人物收集数为 0；未写入存档。每次用不同 query 重新导航得到新文档，但不是重启浏览器进程的操作系统级冷启动。
- 每轮在首页真实点击“图鉴 · 成就”，每轮都是该文档的第一次打开；共 3 轮，指标取中位数。

被动探针只读运行状态，不改游戏 DOM、资源逻辑或存档：

1. 在按钮捕获阶段记录 `openStart = performance.now()`。
2. 在事件冒泡结束后记录同步处理耗时，并同时读取 `window.__galRendered`、`#gal-people .avatar:not([data-lazy-pos])` 的已挂载数和剩余懒加载数。
3. 在随后两个 `requestAnimationFrame` 回调内用 `performance.now()` 采样。本文“首开耗时”采用**点击捕获到第二个 rAF 回调**，即给浏览器至少一次首帧绘制机会后的保守近似；它不是屏幕呈现时间的硬件测量。
4. 在约 100、250、500、1000、2000、3000、4000、5000ms 采样计数。
5. 等待 5 秒采样完成后，执行 10 次向下 650px、再 10 次向上 650px 的真实浏览器滚动。每轮实际到达 `scrollY=3250` 后回到 0。
6. 滚动期间连续记录 rAF 帧间隔 `dt`。按 60Hz 目标估算掉帧：`Σ max(0, round(dt / 16.667) - 1)`；另报 `dt>25ms` 慢帧和 `dt>50ms` 严重慢帧。测量区间包含自动滚动指令之间的间隔，因此同时给出帧数与时长，不只看总掉帧数。

限制：rAF 能发现主线程卡顿，但不能等价于 Android SurfaceFlinger 的真实呈现帧；线上首开还应补 Performance Trace / Event Timing 和虎扑 App 内真机数据。

## 4. 修复方案设计

### 4.1 D1：让懒加载标记真正关闭背景图

在图鉴作用域增加高优先级规则，或把现有懒加载规则改成该作用域：

```css
#gal-people .avatar[data-lazy-pos] {
  background-image: none;
}
```

理由：

- ID 作用域使优先级高于 `.avatar` 和后面的 `.avatar.b2`，无需 `!important`，也不会受第 223 行后置规则影响。
- 只改变 `#gal-people` 内的头像，不影响夺技、人物详情等其他 `avatarHTML()` 场景。
- 元素移除 `data-lazy-pos` 后，此规则自然不再匹配，原有精灵图、`background-size` 和刚写入的 `background-position` 继续生效，无需重复内联 `background-image`。
- 保留现有背景色作为未挂图占位，不改变格子尺寸、收集状态和灰度样式。

必须同时验证计算样式，而不是只检查规则文本：所有仍带 `data-lazy-pos` 的图鉴头像，`getComputedStyle(el).backgroundImage` 必须为 `none`。

### 4.2 D2：只由可见性驱动挂图

#### 删除两条全量挂载路径

- 删除 `__GAL_BATCH` 及 `lazyCells.slice(0, __GAL_BATCH).forEach(mount)`。
- 删除 `rest`、`requestIdleCallback` 和 8ms 的 `while` 续挂循环。
- 保留一次生成 90 格 DOM 和现有 `content-visibility`，本轮不引入虚拟列表或额外分页。

空闲调度适合非必要预热，不应继续承担“最终无视口挂完所有头像”的任务。图鉴打开期间既有的低优先级预热暂停逻辑保持不变。

#### 统一唯一挂载入口

将设置位置、移除属性、计数和按 sheet 请求解码合并为图鉴内部函数，IO 与无 IO 降级都调用它：

```js
function mountGalAvatar(el) {
  if (!el.hasAttribute('data-lazy-pos')) return;
  const sheet = el.classList.contains('b2') ? __sheet2Url : __sheet1Url;
  el.style.backgroundPosition = el.dataset.lazyPos;
  el.removeAttribute('data-lazy-pos');
  window.__galRendered += 1;
  if (sheet && !__sheetAsked[sheet]) {
    __sheetAsked[sheet] = 1;
    enqueueDecode(sheet, 0);
  }
}
```

示意只表达职责合并，实施时可沿用现有命名。要点：

- `window.__galRendered` 每次打开仍归零，但不落盘、不新增存储 key。
- 计数与实际没有 `data-lazy-pos` 的图鉴头像数一致；无 IO 降级也计数。
- 重复回调不会重复计数或重复入队；继续复用 `__sheetAsked` 和 `enqueueDecode()`，不另起 `new Image()` 解码路径。
- 两张精灵图都是整图资源：第一张可见头像需要某张 sheet 时，仍可能解码整张 sheet。本专项实现的是按视口挂图/按 sheet 请求，不声称 90 人会形成 90 个独立图片请求。

#### 在图鉴可见后观察

```js
function openGallery() {
  __galleryOpen = true;
  renderGallery();          // 只构建、重置计数，不挂图
  showScreen('gallery');    // 先脱离 display:none，并回到顶部
  __galObserve($('gal-people'));
}
```

`renderGallery()` 末尾原来的 `__galObserve()` 相应移除。现有重开时 `__galIO.disconnect()` 保留，避免旧观察器继续持有上一批 DOM。

IO 继续使用当前 `rootMargin: '200px'` 作为预挂边界：

- 只对 `isIntersecting` 的格子调用 `mountGalAvatar()` 并 `unobserve()`。
- 不额外恢复“首批 24 格”。图鉴顶部是结局与成就区域时，人物区可能一个都不相交，首屏计数为 0 是合理结果，不应为了固定计数而挂屏外图。
- 不支持 IO 的浏览器保留“全部挂载”的功能降级，确保图片最终可见；该分支不属于正常现代浏览器的性能验收路径。

### 4.3 D3：外置方案、单文件降级与取舍

#### 方案 A：虎扑单文件继续保持内联（本轮推荐）

- 保留两条共享 data URI，实施 D1 + D2。
- 优点：仍是一个可独立运行的 HTML；无新增请求、CSP、CDN、缓存一致性或资源 404 风险；非图鉴头像资源路径完全不变。
- 缺点：HTML 仍需下载约 849,072 B 精灵 base64；不能获得首包减重。
- 适用：当前已明确以虎扑单文件包分发，且尚未证明平台支持伴随静态资源的情况。

这不是“外置后的运行时 fallback”，而是一个完整、可独立发布的分发变体。

#### 方案 B：共享精灵图外置（有实际减重，但有分发前提）

若静态站或经验证的平台支持资源文件：

1. 从当前 data URI 原样解码出两张 WebP，使用内容哈希命名，例如 `assets/gallery-avatar-sprite-1-fba3bdfd02d80a7d.webp`、`assets/gallery-avatar-sprite-2-193e037e0ff342c6.webp`。
2. 将共享 `.avatar` / `.avatar.b2` 的 URL 换成上述外链，保持 `background-size`、`background-position`、`avatarHTML()` 和裁剪数据不变。这样 HTML 才能真正删除约 849,072 B base64。
3. 扩展 `__initSheetUrls()`：当前第 1579 行正则只接受 `data:`，外置后必须能取得相对/绝对 HTTP(S) URL，并让 IO 继续把实际展示所用 URL 送进 `enqueueDecode()`。不要 CSS 用外链、解码队列却仍读全局 data URI。
4. 不增加两张图的 `<link rel="preload">`，否则会把刚获得的按需请求再次变成必下。
5. 资源与 HTML 原子发布；旧外链至少保留到所有可能缓存的旧 HTML 过期。HTML 与图片使用匹配的缓存策略，图片可用长缓存，HTML 不应长期钉死旧哈希引用。

收益：首包下降、HTML 解析字符串减少、图片可独立缓存，并且第一张图可见时才需要对应 sheet。

代价：新增至多两个图片请求；首次可见可能受网络影响；离线、弱网和缓存错误更明显。虽然裁剪和 `avatarHTML()` API 不变，但共享 URL 替换会让**非图鉴头像也从“随 HTML 自带”变为“依赖网络缓存”**，必须补做冷缓存下的夺技、详情回归。若红线要求连这种资源时序变化也不能发生，则方案 B 不在本轮可实施范围内。

#### 方案 C：仅图鉴外置、非图鉴继续内联（不推荐作为减重方案）

可以用 `#gal-people` 作用域给已挂载格子覆盖外链，同时保留全局 base64 给非图鉴使用。这样能隔离非图鉴资源路径，但：

- 两张 base64 仍在 HTML 中，首包不减；
- 浏览器可能同时持有 data URI 与外链两份相同图片；
- CSS 与解码 URL 管理更复杂。

除非只是为了验证 CDN 图像兼容性，否则不应采用。

#### “HTML 仍是单文件 + 图片使用 CDN”不等于自包含单文件

这种形态上传物可以只有一个 HTML，但运行依赖第三方 CDN。上线前必须在虎扑 App 内验证 HTTPS、CSP/域名白名单、CDN 稳定性、弱网与离线表现；浏览器本地测试通过不够。若平台会重写 HTML URL，也要验证图片相对路径的 base URL，不能默认按仓库目录可访问。

#### 运行时图片失败降级的硬约束

- 若外链失败后还要回退到内联 base64，则 base64 必须继续包含在该 HTML 内，减重收益消失。
- 若 HTML 不包含 base64，失败时只能保留背景色/占位并重试，无法保证相同视觉。
- 因此推荐**构建/发布变体降级**：虎扑发布自包含内联版，静态渠道发布外链版；不要在同一个产物里同时携带双份资源来伪装成“既减重又可回退”。

## 5. 风险与回滚

| 风险 | 预防与验证 | 回滚 |
| --- | --- | --- |
| `none` 被 `.avatar.b2` 覆盖，或移除属性后图片不恢复 | 使用 `#gal-people` 作用域；分别检查两张 sheet 未挂载/已挂载计算样式 | 回退 D1 的局部 CSS 改动 |
| 图鉴隐藏时观察导致首屏空白 | `showScreen('gallery')` 后再观察；首屏、滚入人物区各测一次 | 恢复原 `openGallery()` 调用顺序与挂载路径 |
| 重开图鉴出现旧 DOM 回调、重复计数或重复解码 | 保留 `disconnect()`、挂载守卫和 `__sheetAsked`；连续返回/重开测试 | 恢复上一版 `renderGallery()` / `__galObserve()` |
| 第二组头像错位 | 不改 `AVATAR_POS*`、尺寸和裁剪；检查曹操/刘表、夏侯惇/陈兰等每张图首尾位置 | 回退局部挂载代码，不涉及数据迁移 |
| 无 IO 浏览器永远不显示图片 | 明确保留全量挂载降级，并验证计数 | 同上 |
| 外链 404、CDN 被拦截、离线空白 | 虎扑内真机验证；哈希命名；失败演练；自包含版本作为发布降级 | 直接重新发布上一版自包含 HTML |
| 外链新版 HTML 与旧缓存图片不匹配 | 原子发布，旧图片保留；文件名内容哈希 | 切回旧 HTML 时旧图片仍可用 |
| 外置意外改变非图鉴头像冷启动表现 | 冷缓存验证夺技、详情；若不允许该变化则不实施外置 | 恢复共享 data URI |
| 把桌面 0 掉帧误当成移动端验收 | 虎扑安卓真机采用同一采样口径再测 | 性能门槛不以桌面结果豁免 |

所有代码改动都应限制在图鉴 CSS、图鉴挂载/观察函数及（仅外链变体）两条精灵 URL 与其 URL 读取逻辑。无需数据迁移，也不应新增、重命名或清空任何 `localStorage` key。回滚代码和页面资源即可，不涉及存档兼容性。

## 6. 验收指标建议

### 6.1 正确性与“真懒加载”硬指标

1. 仍生成 90 个人物格，已点亮/未点亮样式、灰度、姓名、等级、点击详情均与改前一致。
2. 支持 IO 的正常路径中：
   - 每个带 `data-lazy-pos` 的头像计算样式均为 `background-image:none`。
   - 首开同步返回和静止 5 秒期间，已挂载集合只等于“视口 + 200px 预挂边界”内实际相交的集合；除非它们确实覆盖 90 格，否则不得自动变为 90。
   - 不滚动时计数不增长；滚入新区域后只挂载新相交格，快速滚动最终可正常补齐。
   - 每次采样均满足 `window.__galRendered === 实际已挂载图鉴头像数`。
3. 返回首页再打开，计数重新从 0 开始，旧节点不被重复挂载，解码队列不重复请求同一 sheet。
4. 无 IO 降级能显示全部头像，并明确作为兼容例外，不把其 90/90 误判为缺陷。
5. 夺技、详情等非图鉴 `avatarHTML()` 场景视觉不变；外链变体还必须通过冷缓存与弱网测试。
6. 玩法、数值、存档结构、既有存储 key 完全不变。

### 6.2 性能指标

沿用本文方法，同机同浏览器各跑至少 3 次取中位数：

- 桌面首开第二 rAF：建议不高于 **基线中位数 + 1 个 60Hz 帧**，即约 **37.7ms**，且不新增 ≥50ms Long Task。首开 21.0ms 已很小，本轮不以“必须降低多少百分比”作为唯一目标。
- 桌面快速滚动：建议维持 **p95 ≤25ms、>50ms 帧为 0、60Hz 估算掉帧中位数为 0**。
- 虎扑目标安卓机：先测改前基线，再要求首开不劣化超过 1 帧；建议快速滚动 `>25ms` 帧占比 ≤5%、`>50ms` 帧为 0、p95 ≤33.4ms。若目标机基线已差于此，应至少取得同机改善并记录机型、系统、App 版本、视口和温控状态。
- 5 秒静止期间的挂载集合和 sheet 请求数是比首开毫秒数更稳定的本专项核心指标。

### 6.3 包体与资源指标

内联虎扑版：

- HTML 仍是自包含单文件，人物头像不新增网络请求；不要求 HTML 减重。
- D1 + D2 后，未相交格不触发对应背景图挂图；首次需要某 sheet 时才进入现有解码队列。

外链版：

- 两条头像 data URI 从 HTML 删除，原始 HTML 体积预计减少约 **849,072 B**（扣除新 URL 文本后仍应至少减少约 840,000 B）。
- 线上以相同压缩协议记录 HTML 实际传输体积变化，并分别记录两张 WebP 的冷/热缓存请求。
- 两张文件响应 200、MIME 正确、内容与第 2.3 节哈希一致；未相交 sheet 不请求，首次相交后只请求一次，热缓存重开不重复下载。
- 外链 404 / 离线演练后有明确发布级降级：重新发布自包含内联版，而不是依赖一个并不存在的“免费双份回退”。

## 7. 推荐落地顺序

1. **第一批：D1 + D2，保持内联。** 改动最小，直接消除假懒加载，虎扑单文件与非图鉴资源路径均不变。
2. 用第 6 节硬指标验证，并补至少一台虎扑安卓真机的三次基线/改后对比。
3. **第二批：仅在确认资源托管能力后做外链变体。** 先验证上传、URL、CDN/CSP 和原子缓存，再决定是否替换共享 URL；同步完成非图鉴头像回归。
4. 任一外链验证不通过，发布自包含内联版；D1 + D2 的修复保留，不因 D3 回退而撤回。
